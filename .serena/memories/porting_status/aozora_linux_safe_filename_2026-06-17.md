2026-06-17: Cross-platform AozoraEpub3 safe-filename workspace (Issue #11, Rumia-Channel/narou.rs).

Problem: on Debian/Linux, converting a novel whose title contains `～`(U+FF5E)/`〜`(U+301C) via an AozoraEpub3 route failed with `Conversion error: AozoraEpub3 did not create expected output`. Root cause: `should_use_aozora_temp_workspace` in `src/converter/device.rs` was gated by `cfg!(windows)`, so the risky-char temp-workspace mitigation (added in `aozora_cp932_filename_2026-05-30` / `aozora_interrobang_filename_2026-05-27`) was compiled out on non-Windows. AozoraEpub3(Java) normalizes those chars in its output filename regardless of OS, so the expected path was never found.

Fix (device.rs only):
- Removed the `cfg!(windows) &&` gate from `should_use_aozora_temp_workspace`.
- The Unicode risky-char list (`is_aozora_mapping_risky_char`, formerly `is_windows_aozora_mapping_risky_char`: `〜`/`～`/`−`/`‼`/`⁇`/`⁈`/`⁉`/VS) now triggers the temp workspace on ALL platforms — this is AozoraEpub3-normalization behavior, OS-independent.
- The Windows-31J(CP932) encode-error check (`windows_31j_encode_has_errors`, for `♠`/`♡`/`♢`/`♣`/`𠮷` etc.) stays `cfg!(windows)`-only inside `path_contains_aozora_risky_chars` (formerly `path_contains_windows_aozora_risky_chars`) — it is a Windows path/console-encoding concern.
- Renamed `path_contains_windows_aozora_risky_chars` -> `path_contains_aozora_risky_chars`, `is_windows_aozora_mapping_risky_char` -> `is_aozora_mapping_risky_char` to reflect cross-platform scope. `windows_31j_encode_has_errors` keeps its name. `AozoraInvocation::temporary` / `move_aozora_output` reused unchanged, so the final EPUB filename is restored to the original Unicode name (external output compat preserved).

Scope: only AozoraEpub3-traversing routes are affected (`Device::Kobo` `.kepub.epub`, `Device::Mobi`(kindle) intermediate `.epub`, `convert.use-aozoraepub3=true`, `NAROU_RS_EPUB_ENGINE=aozora`). Native EPUB3 (epub/reader/ibooks default) never reaches this code, so Debian users can also just use native epub (Java-free) as the primary workaround.

Tests (device.rs): split the old `windows_aozora_risky_chars_are_detected` into `aozora_unicode_risky_chars_detected_cross_platform`, `#[cfg(windows)] aozora_cp932_unencodable_chars_detected_on_windows`, and `#[cfg(not(windows))] aozora_cp932_unencodable_chars_not_detected_off_windows`. `aozora_temp_workspace_copies_assets_for_risky_windows_paths` renamed to `..._for_risky_paths` and now asserts the temp workspace on all platforms for a `〜` title. `aozora_temp_workspace_is_used_for_windows_31j_unencodable_paths` is unchanged (still Windows-only for `♠`).
